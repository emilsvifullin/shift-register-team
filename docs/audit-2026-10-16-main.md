## Новые подтверждённые ошибки и исправления

### 1. P2 — закрытие редактора во время записи ломало продолжение операции

В `src/app.js` закрытие карточки сотрудника/ПВЗ обнуляло общий черновик, хотя запрос продолжал выполняться. После ответа сохранение обращалось к уже удалённому черновику. На настоящей странице с задержанным только RPC воспроизведены сохранение сотрудника с последующим `Cannot set properties of null (setting 'id')`, закрытие новой карточки ответом предыдущего запроса и сохранённый ПВЗ с `Cannot read properties of null (reading 'isNew')`.

Та же ошибка в перерасчёте была финансово существеннее: тариф изменён с 3000 до 3300 ₽ для трёх смен; первый запрос удержан, нажата реальная «Отмена», запрос отпущен. Получены `[3300, 3000, 3000]`, закрытое окно и `Cannot read properties of null (reading 'title')` без честного сообщения о частичном результате.

Исправление: независимый снимок операции до ожиданий; запрет редактирования, Escape, фона, отмены и свайпа до завершения записи; проверка принадлежности черновика при ответе. Это охватывает связанные операции карточки, её тарифа и индивидуальной ставки. При отказе перерасчёта обновляются факты с сервера, показывается сохранённое количество, в повторе остаются только неподтверждённые смены. Сохранённые ранее деньги сами по себе не пересчитываются: перерасчёт по-прежнему требует действия администратора.

Постоянное доказательство: `e2e/editor-save-lifecycle.spec.mjs`, девять сценариев. Управляемые задержки и ошибки находятся на границе RPC; интерфейс, обработчики и сборка приложения настоящие. Исходные четыре репродуктора и журнал — в архиве доказательств. Это не утверждение о случившемся производственном инциденте.

### 2. P2 — печатный итог скрывал недоплату при переплате другому сотруднику

В `src/payroll-pdf.js` итоговая ячейка «Остаток» выбирала только переплату, если та была ненулевой. Настоящие модули дали пример: начислено 6000 ₽, выдано 5500 ₽; одному человеку недоплата 1000 ₽, другому переплата 500 ₽. Ячейка «Итого» содержала только `+500 ₽`. Модель отчёта и верхняя сводка были правильными; записи выплат и начисления этой ошибкой не менялись.

Исправление: в смешанном случае показываются обе подписанные суммы — «Не выплачено» и «Переплата»/«Сверх начисленного». Деньги разных сотрудников не взаимозачитываются. Одиночный итог остаётся компактным.

Постоянное доказательство: три новых сценария в `tests/payroll-report.test.js`; оба смешанных случая падали на прежнем коде. Дополнительно отрендерены HTML, настоящий PDF и изображение итогового отчёта; на ширине печатной области A4 688 px горизонтального переполнения нет.

### 3. P2 — конкурентное создание доступа теряло одну привязку

Два запроса `admin-employee-auth` одному сотруднику без аккаунта могли одновременно прочитать `user_id=null`, создать разные Auth-аккаунты, вернуть оба успешных ответа и перезаписать одну связь другой. Первый выданный логин оставался без своего сотрудника.

Воспроизведён текущий текст Edge handler с настоящими таблицами PostgreSQL и всеми 39 миграциями: два ответа 200, два Auth-аккаунта, одна связь. Внешние Auth-вызовы и транспорт управлялись адаптером, два чтения синхронизированы барьером. Настоящий GoTrue не запускался и рабочие аккаунты для воспроизведения не создавались.

Исправление в `supabase/functions/admin-employee-auth/index.ts`: первоначальная привязка выполняется только при всё ещё пустом `user_id`; нулевой результат означает конфликт 409. Проигравший запрос удаляет только собственный новый аккаунт. Сбой очистки сообщается явно; уже существующий аккаунт не удаляется. Интерфейс сохраняет понятное сообщение о конфликте, даже если обновлённая карточка уже имеет связь.

Постоянное доказательство: `tests/employee-auth-race.test.js` выполняет весь handler и настоящий закреплённый Supabase SDK 2.112.3 с управляемым HTTP. Семь сценариев покрывают гонку, повтор, обновление существующего аккаунта, отказ записи/профиля и отказ очистки. На прежнем коде конкурентный тест падает. Повтор на PostgreSQL после исправления: ответы 200/409, один аккаунт и отсутствие потерянной привязки.

### 4. P2 — обновление PWA могло перезагрузить уже открытую несохранённую форму

В `src/pwa.js` решение о безопасности принималось при запросе активации worker, а `controllerchange` доверял прежнему флагу `activating`. Между этими событиями человек мог вернуться на вкладку и начать ввод; приложение всё равно перезагружалось.

Два новых сценария исполняют настоящий `installPwa`: запрос активации в фоне, возвращение на страницу, начало работы/открытие черновика, поздний `controllerchange`. На прежнем коде вместо ожидаемых нуля перезагрузок получалась одна. Исправление заново проверяет безопасность при смене контроллера и откладывает перезагрузку до следующего безопасного момента. Прежние правила первой установки и смены версии другой вкладкой сохранены.

Постоянное доказательство: `tests/pwa.test.js`; весь набор 11/11. События service worker и документа управляемые — это воспроизведение допустимой последовательности, а не измерение частоты сбоя на реальном iPhone.

## Рабочая база и границы выпуска

Разрешение пользователя на выпуск получено отдельно с условием сохранения внесённых данных. До выпуска проверены рабочий проект `shift-register-team`, история 37 миграций и активная Edge Function версии 7. В рабочую базу не переносятся seed, демо, тестовые записи, временные БД и локальные дампы. Две подготовленные миграции меняют схему/функции; они не пересчитывают прежние суммы и не создают сотрудников или смены. Старые выплаты получают только новый признак `is_advance=false`, сохраняя прежний смысл обычных выплат.

Для контроля сохранности до и после выпуска снимаются количество строк и контрольные суммы всех прежних полей 14 public-таблиц и двух таблиц Auth. Новый `is_advance` исключён из сравнения прежних полей. Успешное совпадение фиксируется в отдельном журнале выпуска; чтение не раскрывает содержимое записей. Во время проверки production никакие рабочие финансовые RPC не вызываются.

Supabase Security Advisor по-прежнему показывает предупреждения о доступных authenticated административных SECURITY DEFINER RPC и выключенной защите известных скомпрометированных паролей. Первое само по себе не доказывает обход роли; проверена эффективная авторизация. Второе — неизменённая настройка усиления защиты, не доказательство утечки. [Описание предупреждения RPC](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable), [защита паролей](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection).

Физические телефоны, восстановление резервной копии, все сети операторов и нагрузка рабочей системы не проверялись. Этот ограниченный аудит не означает «проект вообще без ошибок». По рассмотренным путям подтверждены перечисленные дефекты и их исправления; дополнительные гипотезы не объявлялись обязательными правками.
