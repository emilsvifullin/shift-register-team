## Исправление № 1 в этом проходе

Добавлена локальная миграция `20261016042559_serialize_financial_admin_writes.sql`. Общая транзакционная advisory-блокировка берётся **до чтения состояния и до блокировки любых предметных строк** во всех 26 доступных клиенту административных операциях записи. Покрыты переходы периода, смены, импорт, пересчёт, выплаты, каскадные удаления, изменения ставок и карточек, которые могут участвовать в порядке блокировок. Только чтение справочника аккаунтов остаётся без этой блокировки.

Один общий порядок намеренно сериализует административные записи разных месяцев. Чтения остаются параллельными. Для текущего приложения с редкими записями это ограниченный компромисс в пользу корректности; параллельную запись независимых периодов при необходимости следует вводить отдельным изменением с заранее определённым полным набором блокировок.

Существующие реализации перенесены из `public` в `private`. Все клиентские `EXECUTE` на них отозваны у `PUBLIC`, `anon`, `authenticated`. Публичные шлюзы сохраняют прежние имена, типы, значения по умолчанию и права `authenticated`; проверка администратора идёт до блокировки. Сами прежние тела также сохраняют свою проверку прав. Обработка ошибок и завершение транзакции освобождают advisory-блокировку средствами PostgreSQL.

Повтор **исходного** репродуктора после исправления даёт:

```text
save: успешно
close: payroll_period_changed_since_check
status: checked
liveBase: 4000
snapshotDue: null
```

То есть устаревшее закрытие теперь отвергается. Если закрытие получает блокировку первым, последующая запись дожидается его и видит закрытый период; без подтверждения она отвергается.

В `db-tests/financial-contract.mjs` добавлены настоящие конкурентные регрессии: задержанное сохранение против закрытия; закрытие перед сохранением, удалением, пересчётом, импортом и каскадом ПВЗ; освобождение очереди при ошибке и откате; встречные переносы между месяцами; отсутствие клиентских прав у приватных тел и наличие шлюза на каждом доступном admin RPC записи. Прежняя регрессия выплаты сохранена и адаптирована под общий порядок блокировок.

Первый полный прогон до добавления проверки встречных переносов: **37/37** успешно, `/tmp/shift-financial-serialized-db.log`. Дополнительная проверка встречных переносов и окончательный полный прогон фиксируются в итоговом результате текущей задачи.

Отдельная проверка встречных переносов: **1/1**, `/tmp/shift-financial-transfer-db.log`. Общая блокировка — именно транзакционная, с автоматическим освобождением при завершении транзакции, согласно [официальной документации PostgreSQL](https://www.postgresql.org/docs/current/functions-admin.html#FUNCTIONS-ADVISORY-LOCKS).

## Исправление № 9 в этом проходе

`src/network-routes.js` теперь получает **весь ответ записи**, включая тело, за конечный срок 30 секунд. Внутренний сигнал отмены и связь с внешним сигналом сохраняются до конца чтения. При потере ответа, превышении срока или отмене уже отправленного запроса результат помечается `write_outcome_unknown`: «Результат сохранения неизвестен. Обновите данные перед повтором». Тот же POST не отправляется автоматически другим путём. Отмена до отправки не называется неизвестным результатом и не отправляет POST. Отмена по запросу вызывающего не считается неисправностью пути.

В `src/api/result.js` добавлена нормализация этого состояния. Проверка с **реальной закреплённой копией Supabase JS 2.112.3** выявила, что PostgREST при перехвате транспортной ошибки теряет её `code`, но сохраняет имя в `message`; нормализация учитывает этот фактический формат. Это проверено интеграцией через настоящий SDK, а не только прямым вызовом маршрутизатора.

`tests/network-routes.test.js`: **23/23** успешно, `/tmp/shift-bounded-write-tests.log`. Новые случаи: зависание тела после заголовков, отсутствие заголовков, внешний abort при чтении, сигнал объекта `Request`, отмена до отправки, сохранение известного HTTP-отказа, прохождение неизвестного результата через настоящий SDK до `resultData`. Во всех неизвестных случаях проверяется единственная отправка POST. Физическая авария production-сети для доказательства не создавалась.

Миграция проверяется только на отдельном локальном PostgreSQL. Она не применена к production; commit, push, merge и deployment не выполнялись.
