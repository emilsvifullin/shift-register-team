# Обязательный baseline для зарплатных данных

Этот baseline заменяет полный 10/10 release plan для текущей эксплуатации.
Staging, физический iPhone и необязательные UX-проверки в него не входят.

## Уже закрыто в репозитории

- все административные записи идут через явные gateway RPC;
- RLS и negative-тесты для `anon`, обычного `authenticated` и admin
  выполняются в `db-tests/financial-contract.mjs`;
- устаревшие authenticated grants отозваны;
- смены защищены optimistic locking, tombstone удалений и idempotency;
- CI проверяет Node 22/24, PostgreSQL 17 и браузерный smoke;
- migration gate существует и fail-closed без project credentials;
- локальный Auth включает `password_hibp_enabled = true`;
- локальный restore drill выполнен отдельно от production.

## Проверено на рабочем проекте 10 ноября 2026

- Во всех 14 таблицах приложения включён RLS. У `anon` отсутствуют прямой доступ
  к этим таблицам и права на административные RPC. У `authenticated` отсутствуют
  права на прямую запись в эти таблицы.
- Advisor показал 29 доступных авторизованным пользователям шлюзов
  `SECURITY DEFINER` и выключенную проверку утёкших паролей. Для Auth запрос
  включения вернул HTTP 402 из-за тарифа. Повторное чтение подтвердило, что
  настройка выключена. Обнаружено три учётные записи с ролью администратора.
- Список копий провайдера пуст, PITR выключен. Создана логическая копия на Mac
  с включённым FileVault в каталоге с ограниченным доступом. В изолированном
  PostgreSQL 17 восстановлены и сверены данные 42 таблиц. Проверена целостность
  файлов. Копия охватывает зарплатные таблицы, справочники, данные Auth и
  журнал миграций приложения. Настройки сервисов Supabase проверяются отдельно.
- Миграция `20261108004500` прошла на восстановленной копии. Количество строк
  и контрольные суммы прежних полей 14 таблиц приложения совпали. Рабочий сайт
  ещё использует RPC, которые отключает эта миграция.

## Осталось для рабочего проекта

1. Владелец проверяет необходимость трёх административных учётных записей и
   выбирает, включать ли платную защиту от утёкших паролей. Пока настройка
   недоступна, каждому администратору нужен отдельный уникальный пароль.
2. Продолжать резервное копирование по рабочему графику. Хранить вторую
   зашифрованную копию отдельно от Mac. Восстанавливать в отдельную базу.
3. Добавить токен Supabase с правом `database_migrations_read` в секрет
   `SUPABASE_ACCESS_TOKEN` окружения `github-pages` в GitHub. Workflow уже
   задаёт идентификатор production-проекта.
4. Назначить окно релиза. В начале окна сделать свежую копию и снять
   контрольные суммы. Затем применить `20261108004500`, запустить проверку
   истории миграций и публикацию из проверенного коммита. После публикации
   сверить данные, повторить Advisor и проверить рабочий сайт. До обновления
   сайта старые клиенты не смогут сохранить или удалить смену.

## Что сознательно отложено

- отдельный staging-сайт и staging race-run;
- физическая PWA-проверка на iPhone;
- полный mobile/UX release review;
- необязательные P2-функции.

Пока пункты production baseline не подтверждены артефактами, статус остаётся
**Go с ограничениями**. Код и локальные тесты при этом уже готовы к безопасному
release.
